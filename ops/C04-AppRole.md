# Authentifier le bootstrap du control-plane

Depuis le MSI, cibler la VM Vault du tailnet à http://100.91.75.58:8200, montage auth/approle, rôle ansible-vps. Vérifier le transport sans authentification avec curl sur /v1/sys/health. Un HTTP 200 sur cette route établit la disponibilité, pas la validité du couple AppRole.

Avec une session opérateur autorisée, lire auth/approle/role/ansible-vps et vérifier secret_id_num_uses=1 et secret_id_ttl=1200 secondes. Lire role-id sous ce rôle et générer un SecretID neuf par POST sur auth/approle/role/ansible-vps/secret-id. Acheminer les champs role_id et secret_id directement en mémoire ou dans un fichier temporaire privé hors Git (umask 077). Ne pas afficher les réponses ni activer le traçage. Pour Ansible, fournir vault_ansible_role_id et vault_ansible_secret_id dans ce fichier et passer uniquement son chemin avec -e @/chemin/protege/phase2.yml.

Un test consomme l’unique usage du SecretID. Obtenir l’accord explicite de Sébastien, préparer l’accès à l’audit, puis générer un SecretID dédié distinct du bootstrap. Envoyer une seule requête POST JSON avec role_id et secret_id à /v1/auth/approle/login. Désactiver les retries. Conserver en mémoire le token de test pour le révoquer immédiatement par POST /v1/auth/token/revoke-self. Effacer le fichier temporaire après usage. Pour une rotation, générer le nouveau secret, basculer, puis révoquer par accessor les anciens identifiants encore actifs et contrôler leur disparition.

Corréler la fenêtre UTC, le chemin, l’opération et le request.id avec la paire request/response du dispositif d’audit Vault. Consigner uniquement heure, identifiant de requête, code HTTP et catégorie. Aucune réponse HTTP indique un problème de transport ou d’accès au service. HTTP 400/403 indique un refus applicatif, 404 oriente vers le montage, 5xx vers le serveur. Si l’audit ne distingue pas expiration, usage épuisé ou mauvais couple, consigner « cause précise indéterminée ». Un succès actuel ne prouve pas la cause d’un refus historique.
